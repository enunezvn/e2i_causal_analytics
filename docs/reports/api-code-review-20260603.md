## Root-cause themes

1. **Authentication ≠ authorization.** The JWT middleware proves identity but nothing enforces object-/tenant-level ownership → a cluster of BOLA/IDOR PHI leaks.
2. **Fail-open defaults.** Several health checks and read endpoints return success/allow on internal failure.
3. **Silent mocks in production paths.** A few user-visible endpoints return fabricated pharma numbers with no provenance flag.
4. **Raw exception text echoed to clients** across most route modules (information disclosure).
5. **Frontend trusts the wire.** Responses are blind-cast to TS types; a Zod-validating layer exists but is wired into only ~2 call sites.

## 🔴 CRITICAL (confirmed)

### 1. [CRITICAL/security] Auth fails OPEN when Supabase is unconfigured — no production startup guard

- **Location:** `src/api/middleware/auth_middleware.py:245-249 (middleware); src/api/dependencies/auth.py:433-437 (is_auth_enabled); src/api/main.py:742-745 (registration, no prod guard)`  ·  *area: BE authz/security core*  ·  verifier severities: ['CRITICAL', 'HIGH']
- **What:** When SUPABASE_URL or SUPABASE_ANON_KEY are not set, is_auth_enabled() returns False and the JWT middleware logs a warning then passes the request straight through to the handler with no authentication. There is NO startup guard that prevents this in production. By contrast, the CORS wildcard misconfiguration DOES raise a RuntimeError in production (src/api/main.py:680-684), proving the codebase knows how to fail-closed on prod misconfig — but auth has no equivalent. A production deploy that is missing/typos the Supabase env vars silently serves every protected route (patient journeys, HCP profiles = PHI/PII) completely unauthenticated.
- **Impact:** A single missing/misnamed env var in a production deployment exposes all PHI/PII-bearing endpoints to anonymous access. Fail-open on auth in a regulated pharma platform is an exploitable, HIPAA-relevant data-exposure hole that produces no error — only a log line nobody reads.
- **Fix (proposed by reviewer):** Add a hard startup guard in src/api/main.py mirroring the CORS one: `if os.environ.get('ENVIRONMENT')=='production' and not is_auth_enabled(): raise RuntimeError('Auth must be configured in production')`. In the middleware, when ENVIRONMENT is production and auth is unconfigured, return 503 rather than passing through. Keep the pass-through only for explicit dev/test environments.
- **🔵 OWNER DECISION — DO NOT IMPLEMENT THE ABOVE FIX.** The fail-open is intentional: a fail-closed startup guard previously prevented the app from connecting. The actual exposure this finding is concerned with (anonymous reach to PHI) was via the **public allowlist**, which has been fixed (see "Status / actions taken"). This finding is retained for the record only.

### 2. [CRITICAL/security] IDOR: cognitive session read/delete/list trust client-supplied session_id and user_id without ownership check

- **Location:** `src/api/routes/cognitive.py:447-512 (get_session), 564-580 (delete_session), 588-620 (list_sessions), 251-438 (process_cognitive_query)`  ·  *area: BE routes: chat/agents*  ·  verifier severities: ['CRITICAL', 'CRITICAL']
- **What:** The /api/cognitive/* router is JWT-protected by the global middleware (it is NOT in PUBLIC_PATHS), so the caller is authenticated. But none of the session endpoints compare the path/body identifiers against the authenticated principal in request.state.user. get_session(session_id) and delete_session(session_id) take the session_id straight from the URL path and call working_memory.get_session/delete_session with no owner check. list_sessions accepts ?user_id=<anything> from the query string and returns that user's sessions. process_cognitive_query accepts session_id and user_id from the request body and continues any session by id.
- **Impact:** Any authenticated user (lowest viewer role) can read another tenant's cognitive session — which contains the user's natural-language queries, generated responses, and the accumulated evidence_trail (memory content) — by guessing/enumerating a session_id or by passing another user_id to /sessions. In a pharma analytics product these sessions can contain PHI/PII-derived patient-journey and HCP analysis. They can also delete another user's session. This is a cross-tenant data-exposure and data-destruction hole reachable in prod.
- **Fix:** Inject the authenticated user (e.g. user: dict = Depends(require_viewer) or read request.state.user) into each endpoint. For get/delete, fetch the session and 404/403 unless session['user_id'] == authenticated id (or the caller is admin). For list_sessions, ignore the client user_id and scope to the authenticated id. For process_cognitive_query, derive user_id from the token, not the body, and verify ownership before continuing an existing session_id.

### 3. [CRITICAL/security] Unauthenticated public exposure of Patient/HCP graph nodes and relationships (PHI/PII leak, cross-tenant)

- **Location:** `src/api/routes/graph.py:257-322 (/nodes), 451-524 (/relationships), 967-1023 (/stats), 621-721 (/causal-chains)`  ·  *area: BE routes: data/memory/graph*  ·  verifier severities: ['CRITICAL', 'HIGH']
- **What:** GET /api/graph/nodes, GET /api/graph/relationships, GET /api/graph/stats and POST /api/graph/causal-chains are listed as PUBLIC in JWTAuthMiddleware (src/api/middleware/auth_middleware.py PUBLIC_PATHS: ('GET','/api/graph/nodes'), ('GET','/api/graph/relationships'), ('GET','/api/graph/stats'), ('POST','/api/graph/causal-chains')) and have no per-route auth dependency. The /nodes handler returns full node properties via _convert_to_graph_node, which copies ALL node fields except a small denylist (id/type/name/timestamps) into `properties`. The knowledge graph contains Patient and HCP entities (EntityType.PATIENT / EntityType.HCP are first-class; get_node_network has dedicated patient/HCP branches), so node properties can include patient_id, hcp_id and clinical/contact attributes. There is no brand/tenant filter, so a caller reads across all brands.
- **Impact:** Anonymous internet/LAN callers (no token) can enumerate the entire knowledge graph including Patient and HCP nodes and their properties — a HIPAA-relevant PHI/PII breach — and can map causal relationships across every brand. 'public for demo visualization' is not a safe posture for a graph that holds patient data.
- **Fix:** Remove these four graph paths from the PUBLIC_PATHS allowlist and require at least require_viewer; for Patient/HCP node data enforce per-tenant/brand scoping (RLS or explicit brand filter from the user's grants via get_user_brands). If a sanitized demo view is genuinely needed, serve it from a separate endpoint that returns only non-PHI synthetic/aggregate nodes.

### 6. [HIGH/security] Auth middleware fails OPEN when Supabase env is unconfigured (is_auth_enabled() == False)

- **Location:** `src/api/middleware/auth_middleware.py:244-249`  ·  *area: BE routes: chat/agents*  ·  verifier severities: ['HIGH', 'HIGH']
- **What:** When SUPABASE_URL or SUPABASE_ANON_KEY is missing, is_auth_enabled() returns False and the middleware logs a warning then allows the request through unauthenticated — for every otherwise-protected route, including /api/cognitive/*, /api/agents/*, and the copilotkit chat surfaces. Intent is clearly a dev convenience (there IS a separate guard at auth.py:93-101 that disables E2I_TESTING_MODE when ENVIRONMENT=production), but there is NO equivalent production guard for the is_auth_enabled()==False branch. ### 7. [HIGH/security] Rate-limit buckets collapse all /api/* endpoints into one shared counter

- **Location:** `src/api/middleware/rate_limit_middleware.py:285`  ·  *area: BE authz/security core*  ·  verifier severities: ['HIGH', 'MEDIUM']
- **What:** The rate-limit storage key is built as `{client_key}:{path.split('/')[1]}`. For EVERY path under /api/ (i.e. virtually all endpoints), `path.split('/')[1]` evaluates to the literal string 'api'. So `/api/auth/login`, `/api/causal/estimate`, `/api/batch/run`, `/api/admin/...` all share the single bucket `{client}:api`. Meanwhile `_get_limit_for_path` returns DIFFERENT limits/windows per path (auth=20/60, batch=10/60, calculate=30/60, copilotkit_chat=30/3600, default=100/60). The per-endpoint limit selected by the current request is checked against ONE shared, cross-contaminated counter. The dedicated auth limit (20/min, intended to throttle credential brute-force) is therefore not isolated: it is consumed by all other /api traffic, and the windows even differ (a 3600s chat window and a 60s window prune the same in-memory list inconsistently).
- **Impact:** The brute-force protection on /api/auth/login is defeated/unreliable: because the counter is shared and the InMemoryBackend prunes using the current request's window, an attacker can keep the auth bucket's effective behavior unpredictable, and benign high-traffic endpoints can exhaust or interfere with the strict auth/batch limits. The advertised per-endpoint limits do not hold. Intent (distinct limits per category) is clearly present but the keying defeats it.
- **Fix:** Key the bucket by the same category used to pick the limit, not by path.split('/')[1]. Compute a category label inside _get_limit_for_path (e.g. return (limit, window, category)) and build `rate_key = f'{client_key}:{category}'`, or at minimum use the full normalized path. Add a regression test asserting that /api/auth/login and /api/causal/estimate land in different buckets.

### 8. [HIGH/security] IDOR: copilotkit /chat and /chat/stream take user_id from the request body instead of the authenticated token

- **Location:** `src/api/routes/copilotkit.py:3194-3247 (stream_chat), 3250-3369 (chat), 3016-3035 (ChatRequest), 3085 (session_id = user_id~uuid)`  ·  *area: BE routes: chat/agents*  ·  verifier severities: ['HIGH', 'HIGH']
- **What:** Both chat endpoints are gated by Depends(require_viewer), so a valid token is required, but the user_id used for the whole workflow comes from ChatRequest.user_id in the request body — never reconciled with the authenticated principal. run_chatbot/stream_chatbot use that user_id to build session_id as f"{user_id}~{uuid}" and to persist/retrieve conversation + episodic memory.
- **Impact:** An authenticated low-privilege user can impersonate any user_id: messages get written into another user's conversation namespace, and by supplying a victim's user_id plus an existing session_id (the session_id format is user_id~uuid and load_context_node loads prior messages by session_id) they can cause prior-conversation history to be loaded and surfaced. Cross-tenant write/read of conversation data in a PHI/PII product.
- **Fix:** Stop trusting body user_id. Derive user_id from request.state.user['id'] (the value require_viewer already validated) and either drop ChatRequest.user_id or reject requests where it differs from the token's subject. Verify session ownership before loading history for a supplied session_id.

### 9. [HIGH/security] PHI horizontal-access (BOLA/IDOR): /explain/history/{patient_id} returns any patient's SHAP explanation to any authenticated user

- **Location:** `src/api/routes/explain.py:1009-1081 (route: 1009; query 1047; response 1066-1072)`  ·  *area: BE routes: causal/ML*  ·  verifier severities: ['HIGH', 'HIGH']
- **What:** get_explanation_history has NO route-level auth dependency and NO authorization/ownership check. The global JWTAuthMiddleware (src/api/middleware/auth_middleware.py) requires only a valid JWT (any role, including VIEWER) for this path — it does not enforce role or patient/tenant ownership, and this path is not in the public allowlist nor specially scoped. The handler queries ml_shap_analyses by the raw path-param patient_id (`.eq("patient_id", patient_id)`) and returns per-patient prediction_class, prediction_probability and signed SHAP feature contributions (e.g. therapy_adherence_score, comorbidity_count, lab trends). mask_identifier only masks the echoed patient_id string; the PHI-derived model signal is returned in full.
- **Impact:** Any authenticated user (even lowest VIEWER role) can enumerate patient_ids and retrieve another patient's regulatory-audit SHAP explanations — a broken-object-level-authorization PHI exposure. In a pharma platform this is a privacy/compliance breach.
- **Fix:** Add an authorization dependency (at minimum Depends(require_auth); ideally a role + patient/brand-scope check) and enforce object-level ownership — verify the caller is permitted to view this patient (e.g. via get_user_brands / tenant scoping / RLS) before returning rows. Do not rely on the global middleware, which authenticates but does not authorize per-object.

### 10. [HIGH/security] Route forwards raw user entity_types / relationship_types into a layer that string-interpolates them into Cypher (injection at the trust boundary)

- **Location:** `src/api/routes/graph.py:294-307 (list_nodes), 489-507 (list_relationships)`  ·  *area: BE routes: data/memory/graph*  ·  verifier severities: ['HIGH', 'HIGH']
- **What:** list_nodes splits the user-supplied `entity_types` query param on commas with no validation ([t.strip() for t in entity_types.split(',')]) and passes the raw strings to semantic.list_nodes()/count_nodes(); list_relationships does the same with `relationship_types`. The downstream FalkorDBSemanticMemory builds Cypher by direct f-string interpolation of those values: list_nodes/count_nodes do `" OR ".join([f"'{t}' IN labels(n)" for t in entity_types])` and list_relationships does `rel_match = f"-[r:{'|'.join(relationship_types)}]->"`. Because the route does not constrain these to the known EntityType/RelationshipType enum members, an attacker controls Cypher syntax (e.g. entity_types="x' OR true OR 'y" or a relationship type containing `]->()-[...]`), enabling Cypher injection / query manipulation. (The interpolation lives in semantic_memory.py, but the route is the validation boundary that lets untrusted input through.)
- **Impact:** Cypher injection through public, unauthenticated endpoints (/api/graph/nodes and /api/graph/relationships are in the PUBLIC_PATHS allowlist), allowing query manipulation / broadened data exfiltration of the PHI-bearing graph.
- **Fix:** Validate each split value against the EntityType / RelationshipType enums in the route (reject or drop unknown members) before passing downstream, and fix the downstream builder to use parameterized label/type matching rather than f-string interpolation. Defense-in-depth: do both, since the route is the place the API contract is enforced.

### 11. [HIGH/security] Cross-brand IDOR: any Operator can DELETE or disable another tenant's sentinel (no brand-membership check on PATCH/DELETE)

- **Location:** `src/api/routes/sentinels.py:234-257`  ·  *area: BE routes: monitoring/audit/ops*  ·  verifier severities: ['HIGH', 'HIGH']
- **What:** delete_sentinel and update_sentinel only require the OPERATOR role (Depends(require_operator)) and then mutate the row purely by sentinel_id, with NO brand-membership check. delete_sentinel runs client.table("sentinels").delete().eq("sentinel_id", sentinel_id).execute() unconditionally. update_sentinel runs the UPDATE before any brand check, then calls get_sentinel() which only 404s on read-back AFTER the write already committed. The module docstring and create_sentinel/list_sentinels/get_sentinel all enforce per-brand grants (get_user_brands) precisely to stop one tenant touching another tenant's rows, but the two mutating-by-id handlers were missed. An Operator holding only a Brand-X grant can therefore disable or permanently delete a Brand-Y sentinel, or a brand='all' cross-brand sentinel, simply by knowing/guessing its id.
- **Impact:** Cross-tenant authorization bypass on destructive/state-changing operations in a multi-tenant pharma platform. Deleting or disabling a brand='all' sentinel (whose actions cascade invalidation / dispatch agents / notify across the whole platform) silently breaks alerting for other tenants; deleting/disabling another brand's watcher is a denial-of-monitoring and integrity loss. PATCH also leaves the DB mutated while returning a 404, an inconsistent state.
- **Fix:** Before the update/delete, fetch the row, run the same admin-or-brand-grant check used in get_sentinel (`is_admin or row['brand'] in allowed_brands`), and return 404 (to avoid existence leakage) when out of grant — fail BEFORE mutating. Apply the check identically in both update_sentinel and delete_sentinel. Consider a shared helper so the three read/write paths cannot drift again.
