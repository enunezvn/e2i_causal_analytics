codex iter2 (LOW, non-blocking) read the script and found the framing above too
generous. Its SAFETY loop only asserts that no [PENDING] line MATCHES one of three
destructive-filename patterns (rollback_ / _rollback.sql / _validation_queries.sql).
146's name matches none of them, so that loop prints PASS whether or not 146 is
discovered at all. It can detect wrongful INCLUSION; it is structurally blind to
wrongful EXCLUSION, which is the direction that actually matters here. And the
summary output committed above prints only PASS/FAIL lines, never the apply set —
so a reader cannot check it either.

That is a PROXY standing where a CAPABILITY was claimed. Rather than soften the
claim, here is the measurement. Same method — the REAL runner, --dry-run, against a
fresh empty postgres:15-alpine — but keeping the apply set itself:

  total [PENDING] files: 228

  line 129:[PENDING] 143_canonical_volume_kpis.sql
  line 130:[PENDING] 144_per_hcp_trigger_count_columns.sql
  line 131:[PENDING] 145_drop_trx_share_patient_axis_variants.sql
  line 132:[PENDING] 146_drop_legacy_per_hcp_count_columns.sql

146 IS in the fresh-database apply set. And the two line numbers carry the other
half for free: the runner emits 144 at line 130 and 146 at line 132, so the
expand-before-contract ordering is visible in the REAL runner's real output on an
empty database, not only in a sorted() call inside a test.

The total cross-validates independently: 228 here, and deploy_gate_realdb_suite.txt
reports "prod ledger 228 keys" — 227 files already applied under matching keys, plus
the one stale 'deferred/146_...' row from the hand apply. Two different methods
against two different databases agreeing on the same count.
