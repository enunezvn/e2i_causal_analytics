# Feast Feature Repository

This directory contains the Feast feature store definitions for the E2I Causal
Analytics platform: entities, data sources, feature views, and the materialized
registry.

## Layout

```
feature_repo/
├── feature_store.yaml      # Feast project config (offline + online stores)
├── entities.py             # Entity definitions (hcp, patient, territory, …)
├── data_sources.py         # PostgreSQLSource / PushSource / RequestSource defs
├── features/               # FeatureView modules grouped by use case
│   ├── hcp_features.py
│   ├── patient_features.py
│   ├── trigger_features.py
│   └── market_features.py
└── data/
    └── registry.db         # GENERATED — see "Registry lifecycle" below
```

## Registry lifecycle

`data/registry.db` is **generated by `feast apply`** on every deploy and is **not
committed to git** (gitignored via both `*.db` and an explicit
`feature_repo/data/registry.db` rule in the project root `.gitignore`).

Treat the registry the same way you treat compiled artifacts:

- **Source of truth**: the Python files in this directory (`entities.py`,
  `data_sources.py`, `features/*.py`).
- **Build step**: `feast apply` reads those files and writes the registry.
- **Deploy step**: the Feast container (`feastdev/feature-server:0.43.0`)
  re-runs `feast apply` at startup so the registry is always in sync with the
  Python definitions, regardless of what was on disk.

CI runs `feast apply --skip-source-validation` against this directory on every
push (see `.github/workflows/backend-tests.yml` job `feast-apply`) so a broken
feature definition fails before merge.

## Local workflow

### Apply (regenerate the registry)

```bash
# From project root, with the project venv active:
feast --chdir feature_repo apply --skip-source-validation
```

`--skip-source-validation` bypasses the per-source connection check, which is
required when the offline store (Supabase Postgres) is not reachable from the
machine running `feast apply` (e.g., CI runners, a developer laptop without VPN).
The registry is otherwise produced identically and the live serving stack will
still validate sources at materialization time.

### Materialize (load features into the online store)

Materialization is automated via Celery beat (see `src/workers/celery_app.py`):

| Task                                    | Schedule        | Purpose                          |
| --------------------------------------- | --------------- | -------------------------------- |
| `feast-materialize-incremental`         | every 6 hours   | Incremental delta into Redis     |
| `feast-check-freshness`                 | every 4 hours   | Alert when feature data is stale |
| `feast-materialize-full-weekly`         | Sunday 00:00 UTC | Full reload across all FVs       |

To materialize manually (e.g., a backfill from a developer machine):

```bash
feast --chdir feature_repo materialize-incremental "$(date -u +%Y-%m-%dT%H:%M:%S)"
```

## Stores

| Store        | Backend                          | Purpose                                |
| ------------ | -------------------------------- | -------------------------------------- |
| Registry     | SQLite (`data/registry.db`)      | Local catalog of entities/feature defs |
| Offline      | Supabase PostgreSQL              | Historical retrieval for training      |
| Online       | Redis (`redis://redis:6379`)     | Low-latency serving for inference      |

The online store powers `BentoML` predictions via the Feast HTTP serving
endpoint at `FEAST_HTTP_ENDPOINT` (default `http://feast:6566`). See
`scripts/bentoml/e2i_serving_service.py` for the integration.

## Tests

Two integration test files cover the registry-and-serving lifecycle:

- `tests/integration/test_feast_apply_idempotent.py` — runs `feast apply`
  twice and asserts no schema drift between runs (entity/feature-view inventory
  is stable).
- `tests/integration/test_feast_offline_online_parity.py` — for a sampled
  set of entities, asserts that `get_online_features()` returns values
  consistent with `get_historical_features()` from the offline store.

Both tests are gated by `pytest.importorskip("feast")` and skip cleanly when
the optional `feast` dependency or a reachable Feast deployment is not
available. The parity test additionally requires offline+online stores
(Postgres + Redis) and is intended primarily for the droplet, not CI.

## Pitfalls

- **Pydantic env-var expansion is NOT applied** to `feature_store.yaml`. Use
  literal Docker service names (e.g., `host: supabase-db`) — the parser does
  not honour `${VAR:-default}` syntax.
- **Registry hash changes on every apply** even when the schema is unchanged
  (the file embeds `last_updated_timestamp`). Idempotency must be asserted
  structurally — entity names, feature-view names, and the entity-to-FV
  mapping — not via a byte-for-byte file diff.
- The registry is **regenerated, not migrated**. Do not commit it; do not
  hand-edit it. Edit the Python files and re-apply.
